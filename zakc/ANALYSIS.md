# Rust compiler assessment

## Recommendation

Rust is a workable choice for this project's compiler, particularly with two
developers already more comfortable in Rust. The scratch implements the
current supported SD1 pipeline, so this decision can be evaluated on runnable
code. Keep the Python benchmark runner, evaluator, sandbox, and task formats
while considering a compiler migration separately.

The current Python implementation already has annotations and a clean
Pyright check. Rust's main additional benefit is the ability to encode more
compiler invariants in the host language: closed enum variants, exhaustive
matches, ownership, and a checked-program boundary. Zak's own type inference
still requires the semantic algorithm; Rust infers types for the compiler's
implementation, not for arbitrary Zak source automatically.

## What changes in the code

| Concern | Existing Python | This Rust scratch |
| --- | --- | --- |
| Syntax | Lark EBNF + transformer methods | Pest PEG grammar + native AST builder |
| AST | Frozen dataclasses with union aliases | Owned structs and enum variants; recursive children in `Box`/`Vec` |
| Types/operators | Primitive names and operators are strings | `Type`, `BinaryOp`, `UnaryOp`, and `AssignOp` enums |
| Builtins | Set of names plus string branches | `Builtin` enum; `strum` derives parsing, display, iteration |
| Static analysis | Lexical type environments + exception unwinding per statement | Lexical type environments + `Result`, accumulating independent errors |
| Type metadata | `dict[id(node), Type]` tied to object identity | `HashMap<NodeId, Type>` with checked uniqueness; survives moves |
| Name resolution | Checker and emitter each resolve lexical bindings | Checker resolves symbols once; emitter consumes the resolved identities |
| Emission boundary | Public AST accepted and reanalyzed by `transpile` | Only private-constructor `CheckedProgram` can be emitted |
| Python representation | Constructs CPython AST, then `ast.unparse` | Renders Python source, then parses it into RustPython AST |
| Errors | Located records with code/message | Typed code + Zak range + typed cause + Rust context trace |
| Delivery | Imported Python modules | Rust library and standalone CLI; JSON is available for a Python adapter |

The underlying language semantics stay familiar: strict I/R/B/S types,
contextual inference for empty collections, lexical shadowing, recursion,
forward function calls, conservative return-path checking, floor division
for integers, and ordered argument evaluation. Function/global names are
resolved to collision-free Python identifiers, including Python keyword
names supplied in valid Zak.

For example, integer `/` and real `/` select different emission paths through
the checked operand type. Adding a new operator or AST variant now creates
compiler errors at exhaustive matches that need updating. Rust still cannot
prove that an author picked the correct semantics for an operator; shared
conformance tests remain necessary.

## Python AST choice

The [RustPython parser](https://docs.rs/rustpython-parser/0.4.0/rustpython_parser/)
returns an owned Python AST entirely inside Rust. It does not require a
Python interpreter or produce Python-owned CPython `ast` objects. The CLI
prints this tree as Rust debug output, and the library exposes the actual
`ast::Suite` for Rust consumers.

This prototype emits source before parsing that Python AST. This makes a
standalone CLI practical and validates the generated syntax, but it adds a
parse pass and relies on careful rendering. Strings are escaped through
Serde JSON, expressions are parenthesized, identifiers are generated by the
checker, and semantic regression tests exercise evaluation order. A future
compiler could construct a dedicated Python IR or Python AST directly if
that representation provides the desired statement rendering support.

The Zak grammar is a manual PEG translation. [Pest's span/position API](https://pest.rs/book/parser_api.html)
provides source ranges; it does not consume the existing Lark grammar.
Maintaining two syntax files long-term would create drift risk. During a
migration, the existing corpus should be shared as the compatibility oracle;
after migration, choose one grammar as the authority.

## Error type and trait

`CompilerError` substitutes compiler codes for HTTP status codes and keeps
the contextual error-trace pattern from SaúdeBridge. `ErrorType` contains
message, IO, JSON, and unexpected-None causes. `ErrorContext` extends both
`Option` and convertible `Result` values. A single generic Result
implementation also handles `Result<T, CompilerError>` through Rust's
identity conversion, without overlapping implementations.

There are two useful locations:

- **Zak origin:** the relevant source expression/statement, including line,
  column, end position, and UTF-8 byte offsets. Outer `.at(...)` calls preserve
  this first source origin.
- **Rust context:** the implementation file/line/column where `.trace()` or
  `.trace_ctx(...)` attached context. `#[track_caller]` propagates the call site
  through the convenience methods.

For `x:=1;` followed by `out(unknown)`, the diagnostic is `UNDEFINED_NAME` at
Zak `2:5`, plus a Rust trace into semantic checking. IO errors have a Rust
context even when no Zak source could be loaded. The output source map also
lets a future adapter associate generated Python statement lines with Zak
locations. Runtime exception translation is not integrated into the sandbox.

Formatting and enum boilerplate use [derive_more](https://docs.rs/derive_more/latest/derive_more/derive/derive.Display.html),
[strum](https://docs.rs/strum/latest/strum/), and `thiserror`, as requested.

## Evidence and limits

The checked-in Python compiler is untouched. The scratch's verification
report records comparisons with 107 distinct source examples, all 15 stdout
fixtures, all 10 reference programs, 69 hidden cases, and 22 runtime examples.
Matching those cases is evidence for this subset, rather than a proof of
equivalence for every syntactically possible input. The original Python
suite is also run separately to detect accidental workspace regressions.

Independent review found a recursive ternary stack overflow and silent
metadata collisions when independently parsed ASTs were combined. Regression
tests reproduce both. Parsing now rejects excessive branch markers before
recursive PEG descent; checking validates node identities before constructing
metadata. Syntax error byte offsets were corrected as well. These changes
illustrate why Rust's static guarantees complement compiler tests: logic and
resource-budget mistakes still need explicit validation.

The conservative limits in the README are prototype choices. They can reject
large otherwise-valid programs. The grammar has no recovery after a syntax
error; semantic analysis accumulates independently checkable statement errors.
Comprehensions and nested functions remain explicitly unsupported, matching
the existing SD1 compiler. Unicode/literal corner cases beyond the tested
corpus, incremental compilation, and production resource budgets have not
been exhaustively evaluated.

## Integration path

1. Retain this as a parallel implementation while the team reviews its Rust
   ergonomics. The crate adds no dependency to the existing Python service.
2. Add a compiler adapter that invokes `zakc --json` and maps its diagnostics
   to the existing public `line`, `col`, `code`, and `message` response fields.
   Keep richer Rust traces for developer diagnostics. Feed emitted Python
   through the existing sandbox as today.
3. Run both compilers against the same corpus and diagnostics before changing
   the default. Process startup should be measured for the actual workload;
   batching requests or a persistent worker can amortize it. PyO3 is another
   option when an in-process API justifies native extension packaging.
4. Only after agreement on parity and ownership, make the Rust grammar/types
   authoritative and retire the duplicate compiler implementation.

`sandbox.runner.evaluate(..., language="zak")` still imports the Python
compiler today. The scratch harness explicitly feeds Rust-emitted Python to
the sandbox; this task does not silently switch the production path.

## Performance experiment

`benchmark-results.json` records a local warm-process comparison across the
same 25 programs: parse, check, emit, and Python AST validation. Both sides
preload files and warm the parsers. Rust uses an optimized release build;
Python uses this workspace's CPython 3.14.4. Startup, IO, Docker, and model
inference are excluded. The Python public emitter also repeats semantic
analysis, while the Rust checked-program API reuses its analysis; the measured
difference reflects both language and architecture.

One local sample on 2026-10-25 (Rust 1.99.1, CPython 3.14.4) ran 5,000
compilations per implementation. Python took 2.836 s (567 µs/program);
Rust took 0.404 s (81 µs/program), about 7.0× faster for this measured pipeline.
The raw result and reproduction commands are included. This ratio does not
include subprocess startup or claim a corresponding end-to-end speedup.

Treat the result as a small corpus microbenchmark. Familiarity, maintainability,
grammar ownership, packaging, and parity are the stronger reasons to choose
the compiler language. End-to-end benchmark latency still includes inference
and isolated execution.

Final verification: 19 Rust contracts passed; formatting and Clippy are clean;
the existing Python suite passed 358 tests plus three subtests and Pyright
reported no errors. CLI recursive checking, Zak AST JSON, Python AST output,
stdin diagnostics, and structured missing-file errors also passed manual
checks. Git shows only the untracked `zakc/` directory; no commits or tracked
file edits were made for this experiment.
